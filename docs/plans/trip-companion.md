# Feature Plan: Trip Companion

> **Status**: TC-1 ✅ Shipped · TC-2/3/4 📝 Planned · tracked on the
> [board](./README.md) · last updated 2026-07-31

Design for four connected features that turn the Trip Agenda from a
planner into an on-the-road companion:

- **A. Road routing & follow-along navigation** — real driving routes on
  the day map, like Google Maps shows them.
- **B. Location-aware music** — playlist suggestions per province, streamed
  from the owner's self-hosted Navidrome server.
- **C. Explore: trending places & trip essentials** — what's popular where
  you're going, plus the practical stuff: food, bathroom, parking, fuel,
  ATM.
- **D. Khmer voice companion** — spoken agenda reminders and a spoken
  "សូមស្វាគមន៍មកកាន់ [destination]" welcome when you arrive at each stop.

Everything here follows the
existing architecture rules ([ARCHITECTURE.md](../ARCHITECTURE.md),
`AGENTS.md`): pure logic modules with tests, server actions as the only
write path, optional services that degrade gracefully, both locales.

## Shared foundation: province detection

All three features need "which Cambodian province is this lat/lng in?".

- Bundle a simplified GeoJSON of Cambodia's 25 provinces (source: OSM
  boundaries, ODbL — data attribution "© OpenStreetMap contributors" in
  the footer; simplify to keep it under ~200 KB).
- New pure module `src/lib/geo/provinces.ts`: `provinceForPoint(lat, lng)`
  via point-in-polygon (ray casting — no dependency needed), plus province
  name lookup in en + km. Unit tests with known city coordinates
  (Phnom Penh, Siem Reap, Kampot, border cases, out-of-country → null).
- Sits beside the existing `src/lib/trips/geo.ts` (haversine,
  nearest-stop) and follows the same conventions.

## A. Road routing & follow-along navigation

### What ships (and what deliberately doesn't)

Ships: the per-day map draws the **actual road route** between stops
(instead of today's straight polyline), with per-leg distance and driving
time; a **Follow mode** that tracks live position along the route,
highlights the current leg, shows a "next stop" card with remaining
distance/ETA, and flags when you're off-route.

Deliberately not shipping: voice turn-by-turn navigation. A browser tab
can't compete with the Google Maps app (wake locks, battery, background
audio, rerouting liability). The existing **"Navigate" handoff button**
(universal Maps URL, key-free) remains the way to actually drive a leg —
Follow mode is for the passenger/planner view between handoffs.

### Routing provider

New module `src/lib/routing/` behind a small interface
(`getRoute(from, to, profile) → { polyline, distanceMeters, durationSec, legs }`):

1. **MVP: OpenRouteService** hosted API — free tier (~2 000 req/day),
   needs `OPENROUTESERVICE_API_KEY` (server-side env var, optional: unset
   → map falls back to today's straight polylines, exactly the existing
   graceful-degradation pattern).
2. **Scale/offline option: self-hosted OSRM** with the Cambodia OSM
   extract — a single Docker container, same interface, no quota. Fits the
   owner's existing self-hosting setup (Navidrome stack). Documented in
   SCALING.md when it lands.
3. Google Directions API stays a possible third driver if a paid key ever
   exists; not required.

Routes between agenda stops are static → **cache aggressively**: table
`route_cache (id, from_lat, from_lng, to_lat, to_lng, profile, polyline,
distance_meters, duration_sec, fetched_at)` keyed on rounded coordinates
(~10 m precision). A day's routes are fetched once by a server action when
the day map opens and served from cache after that. Free-tier quota then
only pays per *edited* leg, not per view.

### UI

- Day map: route polyline snapped to roads, small per-leg chips
  ("12 km · 25 min"). Total day distance/time in the header.
- Follow mode (toggle on the day map): `watchPosition`, current-leg
  highlight, next-stop card (name, remaining distance via haversine to
  polyline, ETA), off-route warning when > ~200 m from the polyline —
  which links straight to the Navigate handoff.
- Pure logic (`nearestPointOnPolyline`, `distanceAlongRoute`,
  off-route detection) lives in `src/lib/routing/follow.ts` with unit
  tests; components only render.

## B. Location-aware music (Navidrome)

### Context

The owner runs a Navidrome + AudioMuse-AI stack
(`~/Documents/open-sources/Navidrome/`): Subsonic-compatible API on
`:4533`, exposable via Cloudflare Tunnel (HTTPS — required, since the
app is served over HTTPS and phones on the road can't reach
`localhost`). The library is a flat folder with mixed Khmer/international
tracks, so **playlists are the unit of suggestion** — either curated in
Navidrome by hand or generated by AudioMuse-AI.

Integration is HTTP-API-only (Subsonic REST). No Navidrome (GPL-3.0) code
is linked — the MIT/Apache-only dependency rule is untouched.

### Account linking (per user, not env vars)

`/account` gains a "Music server" section: server URL + username +
password form. The server action verifies credentials against
`/rest/ping`, then stores **only** a Subsonic auth pair — random salt +
`token = md5(password + salt)` — never the password. That pair is valid
indefinitely for Subsonic API calls and is revocable by changing the
Navidrome password.

Schema:

```
music_accounts     id, user_id (unique), server_url, username,
                   subsonic_salt, subsonic_token, linked_at
province_playlists id, user_id, province_code, playlist_id,
                   playlist_name, unique(user_id, province_code)
```

New module `src/lib/music/`:
- `subsonic.ts` — thin typed client: `ping`, `getPlaylists`,
  `getPlaylist`, `streamUrl(songId)`, `coverArtUrl(id)`. Pure URL/param
  construction is separated from fetch and unit-tested (auth params,
  URL building).
- `suggest.ts` (pure, tested) — pick a playlist for a province:
  1) explicit `province_playlists` mapping, 2) name match against the
  user's playlists (province name in km or en, e.g. a playlist called
  "កំពត vibes" matches Kampot), 3) fallback: none → UI offers the mapping
  screen.

### Suggestion & playback UX

- Trip day view shows a **music card** when the user has a linked account:
  "You're heading to Kampot — play *កំពត vibes*?" (dominant province of
  the day's stops via `provinceForPoint`; in Follow mode, live position
  wins over planned stops).
- A **persistent mini-player** (layout-level client component): cover art,
  play/pause/next, queue from the playlist. Playback is a plain `<audio>`
  element pointing at Navidrome's `/rest/stream?...` URL — the phone
  streams **directly** from Navidrome through the tunnel; our server never
  proxies audio bytes (zero bandwidth cost, works on Vercel).
- Settings screen to map provinces → playlists (drives suggestion rule 1).
- Post-MVP: AudioMuse-AI's API for mood-based generation ("chill sunset
  drive"), Media Session API for lock-screen controls.

Degradation: no linked account → no music UI anywhere (not an error);
unreachable server → card shows "couldn't reach your music server" with a
retry.

## C. Explore: trending places & trip essentials

### Two data sources, one tab

**1. Trending (internal, free, unique to us).** The app already stores
every public template's agenda items with `place_id`/lat/lng. Aggregate
them: places most added/cloned across `public_template` trips, grouped by
province → "Popular in Siem Reap: Phare Circus, Psar Chas night market…".
Pure ranking module `src/lib/places/trending.ts` (count + recency decay,
tested) over a query in `src/lib/queries/`. One-tap **"Add to my
agenda"** creates a prefilled `agenda_items` row (existing
`addAgendaItem` action). Cold-start is honest: the section hides below a
minimum sample size until enough public templates exist.

**2. Essentials (OpenStreetMap Overpass API, free, no key).** Nearby
search around the live position or the selected stop for the practical
categories: 🚻 bathroom (`amenity=toilets`), 🅿️ parking, 🍜 food
(`amenity=restaurant|food_court`, `shop=convenience`), 🛒 local market
(`amenity=marketplace`), ⛽ fuel, 🏧 ATM, 💊 pharmacy.

- `src/lib/places/overpass.ts`: pure query-builder (tested) + fetcher.
- The public Overpass endpoint is shared and rate-limited → **cache by
  geohash cell + category** in `place_cache (id, cell, category,
  results_json, fetched_at)` with a ~7-day TTL; POIs change slowly.
  Server action checks cache first; one flight per cell+category.
- If `NEXT_PUBLIC_GOOGLE_MAPS_KEY` gains a Places-enabled sibling later,
  a `places/` provider swap is possible — Overpass is the default
  because it's free and Cambodia's OSM coverage of essentials is decent.

### UI

New **Explore tab** inside a trip (next to the day agenda):
- Category chip row (Bathroom, Parking, Food, Market, Fuel, ATM,
  Pharmacy) → distance-sorted list with name, distance ("400 m"), and two
  actions: **Navigate** (existing universal-URL handoff) and **Add to
  agenda**.
- Trending section for the trip's province(s), as above.
- Empty/error states per the house style; works with geolocation denied
  (falls back to searching around the next planned stop).

## D. Khmer voice companion

### What it does

Two voice moments, spoken in Khmer (following the user's locale — English
templates exist too, but Khmer is the point):

1. **Arrival welcome** — when the phone comes within ~100 m of the next
   stop (same geolocation loop as Follow mode), the app plays
   "សូមស្វាគមន៍មកកាន់ [ឈ្មោះកន្លែង]" ("Welcome to [destination]"), shows a
   welcome banner, and offers the existing quest-completion button — so
   arriving, hearing the welcome, and collecting the XP become one moment.
2. **Agenda reminders** — a spoken nudge when a stop's `planned_start` is
   approaching ("១៥ នាទីទៀត ទៅ [ឈ្មោះកន្លែង]" — "15 minutes until…").
   In-app while a trip tab is open; **via the existing Telegram bot as a
   voice message (`sendVoice`) when the app is closed** — reusing the
   Phase-6 bot instead of building Web Push infrastructure.

### Key design decision: pre-generate, don't speak live

The agenda is known ahead of time, so every phrase is known ahead of time.
When a stop is created/renamed (and when a reminder is scheduled), a
server action generates the audio clip **once**, stores it through the
existing upload pipeline (Cloudinary / local disk), and the phone just
plays a cached MP3 at the trigger moment. This avoids the two problems of
live TTS: on-device Khmer voices are unreliable (many Android/iOS builds
ship none), and per-play API calls cost money and need connectivity —
whereas rural Cambodia connectivity at the *trigger* moment is exactly
when you can't fetch anything. Clips are preloaded when a trip day opens.

### TTS provider

`src/lib/voice/` behind a provider interface (`synthesize(text, locale) →
audio bytes`), mirroring the routing-provider pattern:

1. **Primary: a hosted TTS API with Khmer neural voices** — Azure Speech
   (documented `km-KH` neural voices, generous free tier) is the leading
   candidate; Google Cloud TTS is the alternate. **Verify current Khmer
   voice quality/pricing of both before building** (open question 4) —
   pick whichever sounds natural to a native speaker, behind env vars
   (`TTS_PROVIDER`, `TTS_API_KEY`, optional).
2. **Fallback when no key**: browser `speechSynthesis` *if* a `km-KH`
   voice exists on the device; otherwise silent mode — the banner, a
   chime, and a vibration still fire, so the feature degrades to visual
   welcome rather than breaking.
3. Self-hosted open-source Khmer TTS is attractive for the owner's
   self-hosting setup but most open Khmer models (e.g. Meta MMS) are
   **non-commercial licensed** — excluded for this commercial app unless
   a clean-licensed model is found.

### Mechanics & schema

```
voice_clips   id, agenda_item_id, kind (welcome|reminder), locale,
              text_hash, audio_url, generated_at
              unique(agenda_item_id, kind, locale, text_hash)
```

- Pure module `src/lib/voice/phrases.ts`: template → text
  (km + en), tested — including Khmer text assembly (no naive
  concatenation; templates live in the message files per the i18n
  playbook).
- Arrival detection: reuse `src/lib/trips/geo.ts` haversine +
  a debounce rule (inside radius for ≥ 10 s, fire once per stop per day) —
  pure, tested.
- Reminder scheduling for Telegram delivery needs a scheduler: Vercel
  cron hitting a route that finds due reminders (MVP), upgrading to the
  job runner SCALING.md already plans (Inngest/QStash) — this is the
  same prerequisite as Telegram batch sends moving off-request.
- Per-user setting: voice on/off + voice locale (default km). Muted
  respects the phone's silent switch by using a normal `<audio>` element.

### Costs & guardrails

Welcome phrases are ~30 characters; even a 1 000-stop month is ~30 k
characters — far inside any TTS free tier. Clips are cached by
`text_hash`, so renaming a stop back and forth never regenerates.
Telegram voice reminders count as normal bot messages (free, rate limits
apply); they only go to users with a linked Telegram + `chat_id`, same
guard as payment requests.

## Rollout phases (independent — any order works)

| Phase | Status | Contents | New env/schema | External dependency |
|---|---|---|---|---|
| **TC-1 Explore** | ✅ Shipped | Province geo module, Overpass essentials + cache, trending from templates, Explore tab | `place_cache` table | Overpass (free, no key) |
| **TC-2 Music** | 📝 Planned | Navidrome linking, province→playlist mapping, suggestions, mini-player | `music_accounts`, `province_playlists` | Owner's Navidrome via HTTPS tunnel |
| **TC-3 Routing** | 📝 Planned | `routing/` provider + cache, road polylines on day map, Follow mode | `route_cache` table, `OPENROUTESERVICE_API_KEY` (optional) | OpenRouteService free tier (or self-hosted OSRM) |
| **TC-4 Voice** | 📝 Planned | Khmer TTS clips (pre-generated), arrival welcome + spoken/Telegram reminders, voice settings | `voice_clips` table, `TTS_PROVIDER`/`TTS_API_KEY` (optional) | Azure/Google TTS free tier; existing Telegram bot |

When a phase's status changes, update it here **and** on the
[board](./README.md) in the same PR.

Suggested order: **TC-1 → TC-2 → TC-3 → TC-4**. TC-1 needs no accounts or
keys and delivers visible value immediately; TC-3 has the most UI risk and
benefits from the province/geo groundwork of TC-1. TC-4 goes last because
its arrival trigger rides on TC-3's Follow-mode geolocation loop (though
a reminders-only slice could ship earlier — it only needs the Telegram
bot and a cron).

Each phase follows the playbooks (schema → pure module + tests → server
action → UI with en/km strings) and ends with the standard verification
plus a Playwright spec for its main flow. ADRs to write when
implementation starts: "Overpass over Google Places for essentials"
(✅ [ADR-0007](../adr/0007-overpass-over-google-places.md)),
"Subsonic salt+token storage (no passwords)", "OpenRouteService with
provider abstraction".

## Open questions (decide before the relevant phase)

1. **TC-2**: is music per-user (everyone links their own server) or
   app-provided (one shared Navidrome, guests get read-only streaming via
   a shared low-privilege account)? Plan assumes per-user; a shared-server
   mode is a small extension (env-provided default `music_account`).
2. **TC-3**: motorbike routing matters in Cambodia — ORS/OSRM support a
   `driving-car` vs. cycling profile, but true moto routing may need a
   custom OSRM profile. MVP ships `driving-car` only.
3. **TC-1**: ~~minimum sample size before "Trending" shows~~ — decided:
   ≥3 distinct public trips referencing a place (default in
   `src/lib/places/trending.ts`).
4. **TC-4**: TTS provider bake-off — generate the same welcome phrase
   with Azure `km-KH` neural and Google Cloud TTS Khmer (if available),
   have a native speaker pick; confirm current pricing/free tiers. Also:
   should the welcome use the stop's Khmer name when the place has one
   (OSM `name:km` tag, available via TC-1's Overpass data)?

## Improvements (post-ship follow-ups land here)

*Add items instead of opening a new plan doc; set the board row to 🔁
while working on one.*

From TC-1 (shipped 2026-07-31):

- **Playwright spec for the Explore flow** — TC-1 shipped with 36 unit
  tests over the pure modules but no e2e spec yet (the flow needs a
  geolocation mock + an Overpass stub to be deterministic).
- **Shared province borders** — `provinces-data.ts` simplifies each
  province independently (geoBoundaries KHM ADM1, Douglas-Peucker
  0.002°, ~145 KB), so adjacent borders have slivers; `provinceForPoint`
  papers over them with a 2 km boundary snap. A topology-aware simplify
  (shared arcs, TopoJSON-style) would remove the snap heuristic.
- **Overpass resilience** — single endpoint (`overpass-api.de`) today;
  add a mirror fallback (e.g. `overpass.kumi.systems`) and/or request
  coalescing so concurrent cache misses for the same cell+category make
  one flight.
- **Trending province filter at query time** — trending currently ranks
  all public-template stops and filters by province in the page; fine at
  current scale, but a `province_code` column on `agenda_items` (filled
  on write via `provinceForPoint`) would let the DB do it.

Already-known candidates: AudioMuse-AI mood playlists (TC-2), Media
Session lock-screen controls (TC-2), self-hosted OSRM + moto profile
(TC-3), Google Places provider swap (TC-1).
